# Changelog

All notable changes to this project are documented in this file.

## [1.4.0] - 2026-11-22

### ⚠️ Breaking and behavior changes
- **Collection items are validated by default.** Objects whose collection items are invalid now fail validation, where
  before they passed. Opt out per property with `[SkipItemsValidation]`, or globally with
  `<ValidateCollectionItems>disable</ValidateCollectionItems>` in `ValidlyConfiguration`. ([#38], [#32])
- **`pointer` uses JSON names.** The `pointer` of each validation error follows the JSON contract
  (`[JsonPropertyName]` or the naming policy) instead of the C# property name, e.g. `#/userName` instead of
  `#/UserName` with camelCase. ([#33], [#26])
- **`ValidationHttpResult` removed.** The public `Validly.Extensions.AspNetCore.ValidationHttpResult` is replaced by
  `TypedResults.Content`. ([#33])
- **`PropertyNamingPolicy` / `ValidlyNamingPolicy`** replace `JsonNamingPolicy` in the public API. ([#33])
- **Generator and runtime versions must match.** Code generated by `Validly.SourceGenerator` 1.4 calls new members of
  `IInternalValidationResult` and `IInternalPropertyValidationResult`, so it needs `Validly` 1.4. ([#33])

### Added
- **Validation of collection items.** Items of arrays, `List<T>`, `IList<T>`, `IReadOnlyList<T>`, `ImmutableArray<T>`
  and any `IEnumerable<T>` of `[Validatable]` objects are validated like nested objects, including hooks and polymorphic
  items. Errors carry the item index, e.g. `#/lines/1/productCode`. Null collections, null items and a default
  `ImmutableArray` are skipped. ([#38], [#32])
- **Inheritance.** A `[Validatable]` class can inherit from another `[Validatable]` class. Base rules run first, and
  non-validatable classes in between are skipped. Bases from referenced assemblies are supported, including ones built
  with Validly 1.3. ([#37], [#29])
- **Generic classes and records** can be `[Validatable]`. ([#31], [#30])
- **Compile-time JSON names.** When the generator knows the naming policy, JSON names are resolved at compile time, so
  nothing is converted per request. The policy is taken from the `ValidlyConfiguration` option, or detected from the
  ASP.NET Core JSON options configured in the same project (`ConfigureHttpJsonOptions` or MVC `AddJsonOptions` with
  `PropertyNamingPolicy = JsonNamingPolicy.X`). The `ValidlyConfiguration` option always wins over the detection, and
  other `JsonSerializerOptions` instances are ignored: ([#33], [#26])

  ```xml
  <PropertyGroup>
      <ValidlyConfiguration>
          <JsonNamingPolicy>camelCase</JsonNamingPolicy>
      </ValidlyConfiguration>
  </PropertyGroup>
  <ItemGroup>
      <CompilerVisibleProperty Include="ValidlyConfiguration" />
  </ItemGroup>
  ```

  Accepted values are `none`, `camelCase`, `snake_case_lower`, `snake_case_upper`, `kebab_case_lower` and
  `kebab_case_upper`, matching the `System.Text.Json` policies. When the policy can't be determined at compile time, it
  is applied at runtime: `Validly.Extensions.AspNetCore` reads it from the configured `JsonOptions`, and
  `GetProblemDetails` / `GetProblemDetailsJson` take an optional `PropertyNamingPolicy`.
- **VLY0100** warning for an unknown `JsonNamingPolicy` value. ([#33])
- `Validate()` is now generated for classes with nested objects or collections, as long as there are no asynchronous
  validators or hooks. ([#37], [#38])
- `NotEmpty` validator supports structs.

### Fixed
- **Pooled validation results were shared between results.** Property paths and messages could leak between results
  (including across concurrent requests), a failed result could turn into `IsSuccess == true`, and
  `"Collection is full"` could be thrown, e.g. for two validatable children. ([#34])
- Off-by-one bounds in the result collections, e.g. the 17th message of a property overwrote the next property's first
  message. ([#34])
- A validation context could be reused by an unrelated validation, which also changed the equality of records after
  validation. ([#34])
- A null nested `[Validatable]` object is skipped instead of throwing `NullReferenceException`. ([#34])
- Combining large or deeply nested results was quadratic. ([#34])
- Problem-details JSON is properly escaped (quotes, backslashes, control characters). A quote in a message previously
  produced invalid JSON. ([#33])
- Generated code did not compile for `ExitEarly` with nested `[Validatable]` properties or async hooks, or for sync
  hooks that don't await anything. ([#35])
- The generator crashed on validators taking DI service parameters in `IsValid`. ([#35])
- The generator crashed on two `[Validatable]` types with the same name in different namespaces. ([#35])
- A `global using` was copied into the generated file as `using global using ...;`. ([#35])
- Duplicate local variables when several validators of one property return a `ValidationResult`. ([#35])
- The generator is built against Roslyn 4.8.0 instead of `[4.14.0,)`, so it loads on older compilers (.NET 8 SDK /
  VS 17.8) and no longer forces a newer Roslyn on the host. ([#36], [#22])
- The generator package no longer ships the generator DLL in `lib/` or declares dependencies. ([#36])

### Performance
- Nested validation allocates 144 B instead of 200 B and is about 30% faster; flat paths are unchanged (0 B). ([#34],
  [#37])
- One `WeakReference` and one `ValidationContextDisposer` allocation less per validation. ([#34], [#37])
- Vectorized JSON escaping check, and no path segment allocation for one level of nesting. ([#33])
- Valid collections don't allocate. ([#38])
